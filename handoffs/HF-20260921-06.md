# HF-20260921-06 — Candidate Docker deployment: Dashboard session security

**Status:** candidate, not stable. No stable tag or production rollback point has been created.

**Runtime source revision:** `882edd457d6bc76f523fcd617f4b829802929006` on branch
`codex/pdf-pipeline-hardening`. This extends the embedded-media candidate in
`HF-20260921-05.md`; migration head remains `0021_pdf_embedded_media.sql`.

## Scope included

- Dashboard JWT is now held in `misa_flipbook_session`, a same-origin `HttpOnly`,
  `SameSite=Lax` cookie with the existing JWT expiry. The browser no longer persists a
  Dashboard token in `localStorage`; only non-secret UI selection state is in
  `sessionStorage`. An old local-storage token is removed on the next successful login.
- Every unsafe browser request made with that cookie must carry a random,
  double-submit `misa_flipbook_csrf` value in `x-csrf-token`. The API compares the
  two values in constant time and rejects a missing/mismatched value with `403`.
  Bearer API/CLI clients retain their existing stateless contract.
- Authentication checks header bearer first, then the Dashboard cookie. A public-reader
  password grant in the query string still takes priority over a Dashboard cookie, so a
  logged-in owner does not change password-reader behavior.
- Login/logout responses use `Cache-Control: private, no-store`; logout clears both
  cookies. CORS now enables credentials only for explicit `CORS_ORIGIN` entries and
  refuses the unsafe wildcard configuration.
- The Docker configuration exposes `AUTH_COOKIE_SECURE`: it may be `false` only for a
  local HTTP pilot. Any MISA HTTPS deployment must set it to `true` before traffic is
  opened. API and browser continue to use one public origin through Nginx `/api`.
- `cookie_session_security.test.js` is added to CI. It verifies the cookie attributes,
  CSRF denial/acceptance, bearer compatibility, explicit CORS and logout over Nginx.

## Deployment gate

This candidate is ready to hand to DevOps for a Docker **pilot/staging** deployment. Before
opening an MISA production endpoint, DevOps must complete these environment-specific items:

1. Terminate TLS at the approved edge, keep API/worker/Redis/Postgres non-public, set
   `AUTH_COOKIE_SECURE=true`, and give `CORS_ORIGIN` the exact browser origin(s), never `*`.
2. Set `TRUST_PROXY_HOPS` and the upstream allowlist for the real TLS/CDN/load-balancer
   chain; the tested value `1` applies only to the one-Nginx-hop Compose topology.
3. Replace every `.env.example` placeholder through MISA's secret mechanism; rotate the
   Docker pilot credentials rather than promoting them.
4. Take and restore-test a consistent PostgreSQL plus storage backup before cutover; set
   retention, monitoring and an owner for the backup alerts.
5. Run the smoke path after deployment: admin and Creator login, upload/convert/publish
   a representative MISA PDF, private/password reader, download policy, replace/rollback,
   and one desktop plus old/new phone/tablet reader check.

## Compatibility and rollback

There is no schema change in this candidate. Deploy API and web together, so the browser
uses the cookie/CSRF protocol consistently. Existing browser users will sign in once again;
this is intentional because legacy local-storage JWTs are removed rather than trusted.

A code rollback to `HF-20260921-05` is schema-compatible, but its browser uses the former
local-storage token flow, so active users will sign in again after a rollback. It does not
restore application data. For a data rollback, follow the backup/restore procedure in
`HANDOFF.md`; first take a new consistent snapshot of the state being rolled back.

## Limits still open before stable

- Docker browser evidence does not replace the agreed old/new phone and tablet device matrix.
- MISA's real PDF corpus and the intended audio/video codecs still need acceptance testing.
- TLS/CDN cache behavior, final proxy topology, object-storage/HA and a production backup restore
  drill have not been performed in MISA infrastructure.
- No stable tag is appropriate until the user accepts a concrete deployed candidate and those
  operational gates have evidence. Follow `HANDOFF.md` at that point to record image digests,
  the backup reference and the immutable tag.
