# HF-20260921-05 — Candidate embedded PDF media

**Status:** candidate, not stable. No tag has been created.

**Runtime source revision:** `4b82244de928eea1d4abe3a922963f08b559eb6a` on `codex/pdf-pipeline-hardening`, following the Docker
public-edge candidate `fb3f97b` / `HF-20260921-04`.

## Scope included

- F10 Level B baseline handles browser-playable **embedded** audio/video only. The parser accepts
  `/Movie`, `/Screen` with `/Rendition`, and `/RichMedia` Assets only when a `/FileSpec` contains an
  `/EF` stream physically inside the uploaded PDF. It never fetches a URI, local path, redirect or
  file attachment that has no positioned media annotation.
- The worker classifies bytes before saving them; its allowlist is WAV, MP3, Ogg, WebM and MP4.
  Filename and PDF MIME metadata cannot promote an executable or arbitrary file into an asset.
  Defaults are 20 MiB for one media item and 50 MiB total per PDF, configurable with
  `PDF_MEDIA_MAX_BYTES` and `PDF_MEDIA_TOTAL_BYTES`.
- `0021_pdf_embedded_media.sql` permits a revision-scoped `media` asset and extends only the existing
  reader RLS functions. The manifest exposes a random asset ID, never the object key. The same
  public/password/private grant, pinned revision, epoch revocation and cache policy apply to pages,
  audio/video and the original-PDF download.
- Reader overlays native controls at the normalized PDF rectangle. It uses `preload="none"`, never
  autoplays, stops flip-pointer propagation and pauses controls on pages that leave the active spread.
  The asset and download endpoints implement one valid HTTP byte range so native players can seek;
  invalid or multi-ranges return `416` rather than falling back to a full file.
- CI runs a fixture-driven E2E test. The fixture is a small valid WAV in a standard PDF `/Movie`
  annotation; it is a regression artifact, not a substitute for the MISA PDF corpus.

## Compatibility and rollout

1. Deploy `api`, `web`, `pdf-worker`, `worker-convert` and migration `0021` as one protocol change.
   Existing ready revisions remain readable: their old manifests simply have no `media` array.
2. Use the default media limits unless MISA publishes a reviewed media policy. Raising either limit
   increases untrusted-PDF process and storage exposure; do not use an unbounded setting.
3. This candidate assumes the same Docker public edge as HF04. Keep API and storage private and set
   the final `TRUST_PROXY_HOPS`/allowlist from the actual MISA TLS/CDN topology.

## Known limits before stable

- No PDF supplied by MISA with video, audio or the intended codec mix has been tested. `/Sound` raw
  PCM, media in annotations outside the three listed forms, external media, JavaScript, Launch,
  Flash and 3D remain unsupported by design.
- Browser evidence is a Docker desktop browser check. It does not certify old phones, current phones
  or tablets, nor codec support across those devices.
- A native browser's `controlsList="nodownload"` is visual convenience only; it is not DRM. A reader
  authorized to play a media asset can still obtain its bytes during the grant lifetime.
- HF04's production limits remain: no final TLS/CDN/cache-purge verification, object-storage/HA test,
  production backup restore drill or long soak test. GitHub Actions was configured but no hosted run
  was observed in this task.
